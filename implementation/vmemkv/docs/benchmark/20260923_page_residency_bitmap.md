# 常駐ヒントのビットマップ化（2026-09-23）

**管理情報の圧縮は成功したが、従来のBPF版からのthroughput改善は確認できなかった。** 常駐Uniformは従来版とほぼ同じで、案1比では小幅低下。常駐Zipfは案1より速いが従来BPF版を下回った。LTMの差は小さい。13.1MiBの管理表が低下の主因という仮説は、この比較では裏付けられない。ただし、圧縮と同時に参照・登録処理も変わるため、原因を否定・確定する測定ではない。

## 変更

`codex/page-residency-bitmap`を`codex/page-residency-hints`から作成した。参照コミットは`e75746c2d03e0d53edaf566c157aad95172b887c`のまま、既存の未コミット作業を引き継ぐ。製品src/includeは案1のみ。今回も実験ソースコピーだけを変更し、未コミット・未push。

従来は1ページに64bitの世代＋状態を置いていた。今回は64ページを1組とし、常駐ビットマップ8B・再登録禁止ビットマップ8B・共有世代8Bの計24Bにする。現在のT2は1,716,438ページで26,820組、管理本体は13,731,504Bから643,680B（約0.614MiB、約95.3%減）。常駐ビットマップ本体だけなら214,560Bだが、総容量はそれより大きい。mapの割当て・管理費は実測で別記する。

常駐ヒットでは通常、1回の64bitロードとマスクで隣接2ページを判定する。64ページ境界を跨ぐ場合は2回。世代と再登録禁止はヒントミス時の登録に使う。対象は従来同様、不変baseのページ跨ぎ小レコード。既存mincoreとmmap/pread、レコード検証を維持し、pread後登録・8MiB単位の確認・適応制御は加えない。

削除通知は実削除より前なので、BPF側を削除時「登録禁止→世代更新→常駐ビット解除」、追加時「常駐ビット解除→世代更新→登録禁止解除」とする。別ページが同じ64bitを更新し得るためatomic OR/AND/ADDを使う。Getはmincore前の世代を控え、登録前後の世代・登録禁止を調べ、不一致なら登録を取り消す。世代は64ページで共有するため、近隣ページの回収でも確認結果を登録できない場合がある。

登録と後検査の間には一時的に古いヒントが見える可能性があり、取消しが他スレッドの正当な登録も消す場合もある。前者は不変mmapの通常fault、後者は既存mincoreへのフォールバックとなる。経路選択用のヒントであり、ページ固定や厳密な常駐保証ではない。スレッドが登録途中で長時間停止する場合、監視障害、世代番号の周回、複数Store・checkpoint切替の汎用対応は試作範囲外。

## 確認・測定範囲

- GCC 13.4の既存ビルド条件とclang 15でビルド成功。BPF未設定時に1,024キー×3回の全バイト照合とMiss確認が成功した。同じ64bit内／境界を跨ぐ登録、世代変更後の拒否、登録禁止ページの除外を小さく確認した。照合ログの「generation CAS」は流用した旧harnessの表示で、圧縮版は前後確認と取消しを使う。
- sudo実行で専用65ページファイルのBPF追加・削除・再追加、隣のページのビット維持を確認した。専用ファイルは削除、BPFは解除済み。圧縮版は実BPF接続でも1,024キー×3回の全バイト照合とMiss確認に成功した。
- 性能比較は案1／従来8B/page／圧縮版、常駐・LTM × Uniform・Zipf、CPU 0の1スレッド、各2回で計24実行を完了。2回目は版の実行順を逆転した。min_time=2秒。16スレッド・他操作・原因別プロファイルへ広げなかった。
- 既存8,259,552キー、キー16B、80%が1024B値・20%が8B値。Xeon Gold 5418N、Linux 5.15.0-186-generic。常駐High=16GiB/Max=32GiB、LTM High=1GiB/Max=2GiB。mapとrootローダーを同じ一時cgroupに計上し、Get子は一般ユーザーで動かす。
- T2を温めてもヒントは初期未知で、通常のGetを通じて蓄積する点は従来と同じ。今回の比較で圧縮版が改善しても、CPU cache missだけを原因と確定する測定ではない。管理RAM・参照回数・登録処理・共有世代の粒度が同時に変わる。
