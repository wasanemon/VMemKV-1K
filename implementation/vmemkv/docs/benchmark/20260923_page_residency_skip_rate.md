# ビットマップ版のmincore省略率（2026-09-23）

**常駐Uniformでは後半も対象Getの約88%でmincoreが残った。** Zipfでは後半約73%を省略できた。まず「十分に省略できていない」側を確認する根拠が得られた。その後の常駐Uniformの登録・保持確認では、実装不備は検出されなかった（後述）。

## 結果

各分布1回、T2を常駐させた後の100万Get。省略率は「省略回数 ÷ ページ跨ぎ小レコードの対象Get数」。初期・後半の各区間には、対象外も含めて10万Getある。

| 分布 | 初期0〜10万Get：省略／対象 | 省略率 | 後半90万〜100万Get：省略／対象 | 省略率 |
|---|---:|---:|---:|---:|
| Uniform | 126 / 20,746 | 0.61% | 2,384 / 20,630 | 11.56% |
| Zipf | 9,454 / 18,871 | 50.10% | 13,532 / 18,539 | 72.99% |

両分布とも10万Getごとの省略率は順に上がった。Uniformは後半でも88.44%、Zipfでも27.01%がmincoreへ戻るため、「ほぼ毎回省略できているのに速くない」という状態ではなかった。

T2は事前に温める一方、常駐ヒントは初期未知なので、初めて触る対象ページが多ければ、正常な登録でも省略率は低くなる。今回の増加傾向はヒントの蓄積途中という説明と整合するが、登録失敗・失効回数・ユニークページ数は測っていない。従ってバグ・過剰な失効とは断定しない。次の検討方向はヒントの初期登録・蓄積であり、常駐Uniformの課題への対策としてpread後登録を優先する根拠は得られていない。

2回のscopeとGet子は全て正常終了し、CPUとメモリ制限を保存ログで確認した。各回BPFを解除して終了。追加のthroughput比較、LTM・16スレッドへの拡大、pread後登録の実装は行っていない。

## 確認方法

- 比較測定に使った圧縮版のソースを別コピーし、`ticket.active`の回数と、そのうち`ticket.hit`でmincoreを省いた回数だけを加算する。分母は全Getではなく、不変baseのページ跨ぎ小レコードとしてこの経路に入ったGet。
- 1スレッド・CPU 0、常駐Uniform／Zipfを各1回。T2を事前に温め、ヒントは従来同様に初期未知とする。各分布100万Getを連続して実行し、10万Getごとの対象回数・省略回数を保存。初期は最初の10万Get、後半は90万〜100万Getを比較する。
- Getは既存の乱数生成・キー生成・値の全バイト走査を再利用。8,259,552キー、16Bキー、80%が1024B値・20%が8B値、seed=42、Zipf α=1。同じメモリ条件High=16GiB/Max=32GiB、mapとrootローダーも同じcgroup予算に含め、Get子は一般ユーザーで実行する。
- この確認は固定回数の連続アクセスで、Google Benchmarkの較正を通さない。計数コードも追加されるためthroughputとして評価せず、過去の速度測定中の省略率そのものとは扱わない。100万Get後を定常状態と保証するものでもない。
- BPFプログラム、ビットマップの参照・登録・失効、mmap/preadの分岐は変更しない。pread後の登録、8MiB単位の管理、追加の性能比較は行わない。省略率だけでは登録不足・不要な失効・単なる初回アクセスの多さを区別できない。

## 登録・保持の追加確認

**今回の常駐Uniform・1スレッド・100万Getでは、登録・保持の不備は見つからなかった。** 1回の追加確認で終了した。

| 確認項目 | 結果 |
|---|---:|
| 対象Get | 208,357回 |
| 実際のmincore省略／独立記録から期待した省略 | 12,637回／12,637回 |
| 全対象Getでの判定不一致 | 0回 |
| mincoreエラー／非常駐の検出 | 0回／0回 |
| 常駐確認後のページ登録照合 | 延べ391,440回 |
| 登録処理直後にビットが立っていなかったページ | 0回 |
| 記録したユニークページ／終了時の確認済みページ | 370,908／370,908 |
| 終了時に失われていた記録済みヒント | 0ページ |
| Get中のBPF世代増分（追加・削除通知） | 0回 |

初期の確認済みページは0。登録後の取りこぼしや通知による失効ではなく、この対象経路でまだ確認・登録されていないページの多さで、今回の低い省略率を説明できた。1ページ内の通常mmap経路などからは、この実装の常駐ヒントを登録しない点も区別する。全Getのページ初回アクセス数を測ったという意味ではない。

既存BPFの世代更新を使って通知なしと判断しており、カーネル全体の回収を独立に追跡したわけではない。scope・Get子とも正常終了、CPU 0とHigh=16GiB/Max=32GiBをログで確認。BPFは終了時に解除済み。追加の測定・修正には進まなかった。

計数用の別コピーで、mincoreが常駐と返した各ページについて、既存の登録処理の直後に実ビットが立っているか確認する。さらに、確認したページを独立したビット列へ記録し、各Getの省略判定と終了時の保持状態を照合する。BPFの既存世代番号の総和をGet開始前・終了後で比較し、差分0なら対象ファイルの追加・削除通知を観測しなかったとして解釈する。通知が発生した場合、独立記録は失効しないため不一致だけでバグと断定しない。

この確認は常駐・1スレッドの範囲に限定し、速度、LTMでの回収競合、多スレッドの正しさへ断定を広げない。BPF・元の登録・失効・経路選択は変更せず、照合用の情報だけを追加する。

```bash

```
