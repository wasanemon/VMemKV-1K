# BPFで失効させるページ別常駐ヒント：最小試作計画（2026-09-23）

以下は実装前の計画。ユーザーの実行指示を受け、現在は最小試作と1スレッドの比較まで完了した。[試作結果](20260923_page_residency_hints.md)を参照。TSX案の棄却判断は維持する。

## 確認した足場

実機はLinux 5.15.0-186-genericでBPF、BPF_SYSCALL、BPF_JIT、BPF_EVENTS、BTF、MEMCGを有効化したカーネル。clang 15とbpftoolはある。`unprivileged_bpf_disabled=2`で、tracepointディレクトリも非特権では読めないため、ロード等にはsudoが必要。libbpf開発ヘッダーは`/usr/include/bpf/`にはない。必要最小限のビルド準備は実行段階で行う。

上流Linux 5.15の[filemap tracepoint定義](https://github.com/torvalds/linux/blob/v5.15/include/trace/events/filemap.h)にはdev、inode、ページindexがあり、追加・削除を区別できる。[filemap.c](https://github.com/torvalds/linux/blob/v5.15/mm/filemap.c)では削除イベントは実際の削除より前、追加イベントはページキャッシュへの挿入後に発生する。実機のUbuntuカーネルのイベント定義・挙動はsudoによる小さな確認を残す。

[BPF array map](https://docs.kernel.org/bpf/map_array.html)はLinux 5.5以降にBPF_F_MMAPABLEを使用可能。各要素は8B境界に配置されるため、1要素を1ページに対応させたmapを256KiBと見積もらない。

## 実行計画

1. `codex/page-residency-hints`を切り出し、既存未コミット作業を保持する。比較基準は案1の実験用コピー。製品src/includeは案1のみを維持する。
2. sudoで対象イベント・mmap可能なmapのロードを確認する。小さな専用ファイルを使い、ページの読込み→解放→再読込みが共有状態に反映されることを先に確認する。BPFはdev/inodeで固定T2を絞り、ユーザー空間へのイベント転送キューは設けず、共有mapを直接更新する。
3. 固定checkpoint1個の不変base・ページ跨ぎ小レコードだけで常駐ヒントを参照する。対象2ページが確認済みなら既存のbase_mmap_scanから読む。それ以外は案1のmincore→mmap/pread。ページ内小レコード・8Bインライン・tail・Scanは既存どおり。ロード失敗時は案1を使う。複数Store、checkpoint切替、イベント監視の自動再接続などの汎用対応は含めない。
4. 下記の競合対策と少数キーの値照合を確認後、常駐/LTM × Uniform/Zipf・1スレッドを各版2回、計16実行。常駐確認の省略・失効を確認するためのカウンターは動作確認だけに使い、通常比較はthroughputを対象にする。
5. 常駐で改善しLTMで明確な低下がなければ、同じ4条件の16スレッドを各版2回追加。明確なLTM悪化、競合対処や必要準備の過大化が判明したら拡大せず結果を記録する。Scan、書込み単独、他サイズ、網羅的テストへは広げない。

## 競合対策の候補

単なるビット消去や、削除通知で世代だけ進める方式にはしない。ページごとに世代番号と「未知／確認済み／再登録禁止」の状態を持つ。

- 削除イベント：世代を更新し、再登録禁止にする。実際の削除が終わるまでのmincoreが常駐を返しても登録しない。
- 追加イベント：世代を更新して未知へ戻す。挿入直後は読込み完了とは限らないため、このイベントだけで確認済みにしない。
- Getの登録：mincore前に世代・状態を読み、mincoreで常駐が確認できたページを、同じ世代の未知状態である場合だけCASで確認済みにする。
- Getの参照：対象2ページの確認済み状態を通常のatomic loadで見る。再登録禁止・未知・範囲外は既存経路へ戻す。

削除→再追加→確認結果登録の順序や世代変化を小さく確認する。これは設計候補で、実機検証前に競合を解消できたとは扱わない。ヒント参照直後の回収、PTEの解除は防がない。ページ固定やfault不発生の保証ではなく、不変baseを既存のmmapで読む経路選択の情報として扱う。

## 容量と公平な比較

最初は世代＋状態を1ページあたり64bitで持ち、ビット圧縮や独自ロックを作り込まない。現T2の7,030,530,024Bでは1,716,438ページ、状態本体13,731,504B（約13.1MiB）。8GiBなら16MiB。mapの管理情報・ローダー等は別に加わる。

BPF mapは測定用cgroup内で作成し、ローダーを含めて同じ予算に算入できることを確認する。外部cgroupで確保したmapを計上せず比較しない。LTM High=1GiB/Max=2GiB、常駐High=16GiB/Max=32GiBを維持する。既存データ、CPU配置、測定時間、反復順を両版で揃える。

採用判断は常駐Getの回復とLTMのthroughputを合わせて行う。イベント処理はシステム全体の追加・削除イベントで呼ばれてから対象を絞るため、その起動負担も残る。保存容量は増えないが、管理RAM、回収・追加時のCPU費用、BPF権限とカーネル依存というトレードオフを結果に明記する。
